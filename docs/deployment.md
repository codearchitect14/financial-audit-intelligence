# Deployment

Three pieces deploy independently: a managed Postgres, the API, and the static
frontend. Configuration templates are in [`infra/deploy/`](../infra/deploy/).

> **These steps require your own accounts.** Nothing here can be executed from
> the repository alone: Neon, Render, and Vercel each need an account, a
> project, and secrets that must never be committed. Treat this as a runbook to
> follow, not a script to run.

---

## 1. Database: Neon or Supabase

Both free tiers include pgvector.

1. Create a project and a database.
2. Copy the connection string. It will look like
   `postgresql://user:password@host/dbname?sslmode=require`.
3. Confirm pgvector is available:

   ```sql
   CREATE EXTENSION IF NOT EXISTS vector;
   ```

   Migration `0001` runs this itself, so this is only a pre-flight check. It is
   in the migration precisely because a managed provider never runs the
   container init script that creates it locally.

**Free-tier characteristics to plan around.** Neon suspends a project after a
few minutes idle, so the first request after a quiet period pays a cold start
of a second or two. Storage and compute hours are capped. Neither is a problem
for a demonstration deployment; both are a problem for production traffic.

## 2. API: Render

[`infra/deploy/render.yaml`](../infra/deploy/render.yaml) is a blueprint. Point
Render at it, or create the service by hand with the same settings.

Set these in the Render dashboard, not in the file:

| Variable | Value |
|---|---|
| `DATABASE_URL` | The Neon connection string from step 1 |
| `CORS_ORIGINS` | Your frontend origin exactly, for example `https://ledgerline.vercel.app` |
| `SEC_USER_AGENT` | `YourOrg your.email@example.com`, a real contact address |
| `GROQ_API_KEY` | Optional. Without it, narrative generation is unavailable |
| `GEMINI_API_KEY` | Optional fallback provider |

`JWT_SECRET_KEY` is generated by Render and kept stable across deploys. Do not
set it by hand and never commit one.

**Migrations run as a pre-deploy command**, not at application start-up. Running
them at start-up races when more than one instance boots, and two processes
applying the same revision concurrently is how a schema ends up half-applied.

### What will not work on the free plan

| Limitation | Consequence | Mitigation |
|---|---|---|
| No persistent disk | Uploaded files vanish on restart | Move `UPLOAD_DIR` to S3 or MinIO before storing anything you cannot re-upload |
| Instance sleeps after 15 minutes idle | First request after a quiet period takes 30 to 60 seconds | Documented for users, or a paid instance |
| ~512MB memory | One worker only, `WEB_CONCURRENCY=1` | The ONNX embedding model loads per worker; two will not fit |
| Ephemeral filesystem | The embedding model re-downloads on cold start | Bake it into the image, or accept the first-request cost |

The memory limit is the reason the platform uses `fastembed` over
`sentence-transformers`: torch alone is roughly 800MB installed and cannot run
on this plan at all.

## 3. Frontend: Vercel or Netlify

Pick one. Both configs are provided.

**Vercel.** Copy [`infra/deploy/vercel.json`](../infra/deploy/vercel.json) to
`frontend/vercel.json`, replace `REPLACE-WITH-YOUR-API-HOST` with your Render
hostname, set the project root to `frontend`, and deploy.

**Netlify.** Copy [`infra/deploy/netlify.toml`](../infra/deploy/netlify.toml) to
the repository root, replace the same placeholder, and deploy.

Both configs proxy `/api/*` to the API so the browser sees a single origin.
That is deliberate: it removes CORS from the picture entirely, and it means the
frontend needs no `VITE_API_BASE_URL`.

Both also declare an SPA fallback. Without it, any deep link such as
`/app/statements/<id>` returns the host's own 404 and never reaches the router.
This is the single most common way a working SPA appears broken in production,
because it only affects a direct visit or a refresh, never in-app navigation.

### Content Security Policy

Both configs ship a CSP. `style-src` includes `'unsafe-inline'` because Tailwind
injects styles at runtime; nothing else is relaxed. If you add an analytics
script or an embedded widget, the CSP must be widened deliberately rather than
removed.

## 4. Loading data

The deployed API has an empty database. Ingestion is a batch job, not something
the web service does.

```bash
# From a machine with the deployed DATABASE_URL exported:
cd backend
DATABASE_URL="postgresql://..." uv run python ../scripts/ingest.py 2023q1
DATABASE_URL="postgresql://..." uv run python ../scripts/analyze.py --benford
DATABASE_URL="postgresql://..." uv run python ../scripts/index_documents.py
```

Run these from your own machine or a scheduled job, not on the web instance:
a DERA quarterly archive is several hundred megabytes uncompressed and will
exhaust a free-tier instance's memory and disk.

## 5. Monitoring

`/api/v1/health` is the liveness probe and touches nothing.
`/api/v1/health/ready` reports on the database and pgvector individually.

Point a free uptime monitor (UptimeRobot, Better Stack) at `/api/v1/health` on
a 5-minute interval. On Render's free plan this has a useful side effect: it
keeps the instance from sleeping, which removes the cold start for real users.

Watch `/api/v1/llm/budget` if you have configured a model provider. It reports
calls against the daily ceiling in a rolling 24-hour window.

## 6. Post-deployment checklist

- [ ] `GET /api/v1/health/ready` returns `{"database":"ok","pgvector":"ok"}`
- [ ] `GET /api/v1/docs` returns 404 (interactive docs are disabled in production)
- [ ] Registering an account works from the deployed frontend
- [ ] A deep link such as `/app/dashboard` loads on a fresh browser tab
- [ ] `CORS_ORIGINS` contains your frontend origin and no wildcard
- [ ] `JWT_SECRET_KEY` is not the development default. The application refuses
      to start if it is, so a successful boot already proves this
- [ ] Response headers include `Strict-Transport-Security`
- [ ] `SEC_USER_AGENT` carries a real contact address before running ingestion

## 7. Rollback

Deployments and migrations roll back separately.

**Application.** Render keeps previous deploys; roll back from the dashboard.

**Schema.** Every migration in this repository has a tested `downgrade`, and CI
verifies the round trip on every run.

```bash
cd backend
DATABASE_URL="postgresql://..." uv run alembic downgrade -1
```

Roll the application back *before* the schema, not after. An old application
against a new schema is usually fine; a new application against an old schema is
not, because it will reference columns that no longer exist.

A migration that drops a column is not reversible in the way this implies: the
downgrade restores the column but not the data in it. Take a database snapshot
before any deployment that includes a destructive migration.
