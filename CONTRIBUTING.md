# Contributing

## Branching

```
main                  protected, always deployable
feature/<short-name>  new work
fix/<short-name>      bug fixes
chore/<short-name>    tooling, dependencies, docs
```

Branch from `main`, keep branches short-lived, and rebase rather than merge `main` into
a feature branch.

## Commits

Conventional Commits, with a scope where one applies:

```
feat(api): add statement detail endpoint
fix(db): use func.now() so timestamp defaults are not frozen constants
chore(ci): audit the lockfile instead of the installed environment
docs(data-model): explain the three-valued fraud label
```

The body should explain **why**. The diff already shows what changed.

## Before opening a pull request

All from `backend/`:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy src
uv run pytest
uv run alembic check
```

CI runs the same set plus a migration round-trip, a dependency audit, and a secret
scan. A red pipeline is not a formality; do not request review on one.

## Code standards

- **Python 3.12**, fully type annotated. `mypy` runs in strict mode.
- **Configuration** is read only through `fai.core.config.settings`, never
  `os.environ`.
- **Errors** are `AppError` subclasses, never bare `HTTPException`, so the response
  envelope stays consistent and internal detail never leaks.
- **Logging** is structured key-value `structlog`, never f-strings. Never log secrets,
  tokens, prompt text, or raw financial figures.
- **Comments explain why.** A comment restating what the code does is noise; rename
  something instead. A comment explaining a non-obvious constraint is valuable, and
  this codebase has several.
- **Tests accompany behaviour changes.** Tests requiring a database are marked
  `@pytest.mark.integration` and must skip cleanly without one.

## Migrations

Never hand-edit an applied migration. Generate a new one.

Always review autogenerated output before committing; it is a starting point, not an
oracle. See [docs/development.md](docs/development.md) for the required round-trip
check.

## Security

- Never commit a `.env`, key, or credential. `.gitignore` covers the common cases and
  CI runs a secret scan, but neither is a substitute for checking your own diff.
- Validate every request body with a Pydantic model.
- Use SQLAlchemy constructs or bound parameters. Never build SQL by string
  interpolation.
- Treat all retrieved document text and uploaded content as untrusted data, never as
  instructions to a model.

## Review

A reviewer is expected to check that the change does what the description says, that
its failure modes are handled, and that anything non-obvious is explained in a comment
or in `docs/`. Approving a diff you do not understand helps nobody.
